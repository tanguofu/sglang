# DFlash2 on gfx942 for GLM-5.3

## Scope and safety

- All changes stay in this isolated worktree on branch `dflash2-gfx942`.
- Do not deploy, restart, or change production Helm values in this phase.
- Do not enable DFlash2 on HIP by default; use an explicit environment gate.

## Implementation phases

1. Port upstream DFlash2 selector and quantized `lm_head` support.
2. Add the missing DFlash PD disaggregation path.
3. Gate HIP behind `SGLANG_ENABLE_DFLASH_HIP=1`.
4. Add correctness tests for selector logits, greedy exactness, sampling, top-k determinism, batch invariance, and PD metadata.
5. Add AIter GEMM/top-k integration only after the reference path is exact.
6. Benchmark on MI308X against the current NEXTN baseline.

## Acceptance gates

- Greedy output is token-for-token identical to the target-only reference.
- Sampling does not change output distribution beyond numerical tolerance.
- Decode throughput median improves by at least 20%.
- No quality regression in 200K/300K needle, AIME 10/10, or six-concurrency checks.
- No retract, watchdog, or transfer failures during benchmark and soak.

## Benchmark matrix

- Context: 100K, 300K, 1M.
- Concurrency: 1, 4, 8.
- Baseline: current NEXTN.
- DFlash2 stages: reference GEMM/top-k, AIter GEMM, AIter GEMM + AIter top-k.
- Metrics: decode tokens/s, accept length, TTFT, ITL, GPU utilization, memory, and failure counters.

## 2026-09-26 quality alignment check

The Flash and 1P1D services are not an apples-to-apples quality baseline:

- Flash uses `/data/model/glm53-flash` with DFLASH.
- 1P1D uses `/data/model/glm53-fp8` with NEXTN.
- The model weights and speculative algorithms are therefore different, so
  100% output alignment with 1P1D is not a valid acceptance gate.

A 20-prompt deterministic comparison used temperature 0, `ignore_eos=true`,
64 output tokens, no logprobs, and the Flash tokenizer to re-encode both text
outputs. All 20 requests on both services returned HTTP 200:

- First token equal: 20/20 (100%).
- Exact text match: 0/20 (0%).
- Exact token match: 0/20 (0%).
- Average common prefix: 21.25 tokens, about 33.2% of the shorter output.

The outputs often agree on the task and answer (for example, both compute
7+8=15 and both produce `HELLO WORLD`), but diverge in wording. This measures
cross-model alignment, not DFlash2 losslessness.

### Logprobs path defect and fix

A logprobs probe on image `20260926c` crashed all eight TP schedulers with:

```text
TypeError: compute_spec_v2_logprobs() got an unexpected keyword argument 'chain_stride'
```

The decode pod restarted and `/health` returned 200 afterward. The worktree now
maps DFlash's linear chain to the standard spec-v2 contract by constructing a
`[batch, block_size]` accept-index matrix and passing `block_size - 1` as the
speculative step count. A regression test locks this call contract. The fix is
not included in deployed image `20260926c`. Image
`glm53-flash-ts4-dflash2-ck-20260926d`
(`sha256:c3f3b300749e37d25cf9d1f10812914ffcebb0ceccb5f31e1a9e1fb0214be153`)
contains the fix and has been pushed, but it is not deployed. Do not enable
logprobs on `20260926c`.

Operational note: a later in-pod unit-test run coincided with a second decode
restart (exit code 0, no new `chain_stride` exception). The service recovered
and stayed healthy afterward. Do not run kernel/unit tests inside a serving
decode pod; use a separate GPU test deployment.

### New AIter tuned-config gap

The live prefill log contains 26,520 `not found tuned config` lines in 24 hours
across 13 GEMM type + `(N, K)` groups: 7 A8W8 block-scale groups and 6 BF16
groups. The current GLM-5.3 tuned CSVs only cover `M <= 64`; prefill observes
raw `M` values from 68 to 7,838. AIter pads these to buckets such as 80, 96,
112, 128, 160, 192, 224, 256, 320, 384, and 512, but those rows are absent.
This forces the FP8 and BF16 GEMMs back to default or torch paths.

This is now the highest-confidence deployment-level optimization:

1. Collect the padded-M buckets for the 13 observed shapes.
2. Run the existing AIter tuner on a separate GPU pod, not inside a serving pod.
3. Merge only `gfx942,cu_num=80` rows with real kernels and bounded error.
4. Re-run the 200K benchmark and full GSM8K before and after the CSV change.

### 2026-09-26 AIter tuning driver

`docker/rocm-mi308x-glm52-pd/scripts/tune_dflash2_gfx942.py` now provides a
safe two-stage driver:

1. `--mode prepare` parses both BF16 and A8W8 miss formats, computes AIter
   gl0 padded-M buckets, and writes tuner-compatible input CSVs. It is CPU-only
   and does not import AIter by default.
2. `--mode tune` explicitly invokes the AIter BF16 and A8W8 tuners, then writes
   filtered `gfx942,cu_num=80` rows with a real kernel, positive latency, and
   error ratio at most 0.05.

The local padded-M rule matches upstream AIter `getPaddedM` at commit
`b727e788b4fe24e9498fda0a5d384c2cb96d83d0`. `--pad-m-source aiter` can compare
against the installed operator in the tuning pod. The driver tunes gl0 buckets
by default; `--include-gl1` is an optional fallback because AIter checks gl0
before gl1.

Running `prepare` against the real 24-hour prefill log produces:

- 144 BF16 tuning rows
- 168 A8W8 tuning rows
- 312 total rows across 13 groups

All six GPU nodes currently have all 8 GPUs requested by serving workloads. Do
not run the tuner inside a serving pod or share a serving GPU. Wait for a
dedicated tuning pod/node, then run:

### Remaining kernel opportunities

- **Small-M selector top-k:** TP8 uses AIter top-k only when selector rows are
  at least 32. At `M <= 28`, AIter is 8–10% slower than torch. A specialized
  small-M top-16 kernel is the main single-request opportunity.
- **Sparse sampling accept:** `_selector_sampling_accept` scatters the selector's
  top-k q into a dense `[batch, gamma, vocab]` buffer, and the DSpark Triton
  kernel reads that full buffer twice. A sparse kernel that consumes
  `candidate_ids` and `q_rows` directly would remove the dense buffer and most
  q reads. This helps sampling workloads; greedy requests bypass this path.
- **Sparse sampling accept implementation:** the worktree now contains
  `chain_speculative_sampling_sparse_triton`. The worker extracts the selected
  draft-token q values and passes `candidate_ids`/`q_rows` directly; the final
  residual subtracts only those top-k q entries. CPU reference tests cover
  selected-q extraction, dense-scatter residual equivalence, and NaN-q handling.
  Before rollout, run GPU parity against the dense kernel for greedy/sampling,
  partial acceptance, all-accepted, rejection, and NaN rows, then benchmark
  sampling traffic. Do not deploy this path from CPU tests alone.
- **Fused GEMM+top-k epilogue:** the selector still materializes full logits
  before top-k. A fused epilogue would reduce HBM traffic, but it is a larger
  kernel rewrite and must preserve index-exact behavior.
- **Host-side allocations and copies:** `_commit_accept` and the selector graph
  still allocate or copy small tensors each step. These are lower priority than
  the CSV and top-k work.

The Mooncake `MC_DISABLE_HIP_TRANSPORT=1` patch is visible in live logs. The

```text
event_loop_overlap_disagg_decode
→ process_decode_queue
→ pop_preallocated
→ _pre_alloc
→ HybridReqToTokenPool.alloc
→ torch.stack(mamba_indices)
→ torch.OutOfMemoryError
```

PyTorch reports 131.07 GB allocated and 0 bytes free while `rocm-smi` reports

exhaustion, not physical HBM exhaustion and not a DFlash2 forward kernel.
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False` and the Mooncake HIP
transport patch did not fix the OOM.

Follow-up on 2026-09-27 narrowed the trigger to Mooncake RDMA registration:
decode logs `available_gpu_mem=51.58 GB`, then each TP rank registers 135 GPU
buffers, and the first small PyTorch allocation fails with 0 bytes free. The
135 entries include the full-attention KV buffers and the hybrid model's
per-layer Mamba state entries. `rocm-smi` still shows roughly 55 GB physical
free after registration, so the NIC/driver is reserving that free HBM rather
than the model exhausting it.

The worktree already contains a decode-only host-staging path for Mooncake KV
registration (`SGLANG_PD_HOST_STAGING=1`), but image `20260927i` does not
contain that code; setting the env alone is a no-op. The next image must be
built from this worktree, then the canary should verify that host staging is
visible in decode logs and that the first request no longer OOMs.

Helm revisions 13–15 are marked failed, but the live StatefulSets and Pods are
correctly on `20260927i`. Do not roll back those revisions blindly. The next
debug step is to instrument `HybridReqToTokenPool.alloc` or `_pre_alloc` with
`torch.cuda.memory_summary()`, `hipMemGetInfo`, and `torch.cuda.memory_stats()`
immediately before `torch.stack(mamba_indices)`. Also inspect
`process_input_requests` and `SchedulerRequestReceiver.recv_requests` for
first-request GPU allocations, and verify that
`SGLANG_MOONCAKE_CUSTOM_MEM_POOL` is unset.
