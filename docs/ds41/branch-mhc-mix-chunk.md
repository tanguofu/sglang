## 解决什么

mHC 的 mixing projection 的算术**随 M 变化**：rocBLAS 在 16/17 换一次 regime、
在 32/33 又换一次（gfx942、K=20480 实测 17 µs / 33 µs / …）。于是
**同一行的 fp32 累加顺序取决于这个 batch 恰好有多少行**。

投机解码开着时（gamma=3）forward batch 是 `4 * bs`，切换点落在生产 decode
实际会走到的范围内。

## 开关与默认值

| 项 | 值 |
|---|---|
| 环境变量 | `SGLANG_DS41_MHC_MIX_ROW_CHUNK` |
| 默认 | `"0"` = **今天的行为**：整批一次调用 |
| 语义 | 设成 N 后，`M > N` 的批次按 `ceil(M/N)` 次 N 行调用；`M <= N` 仍是单次调用 |
| 实测取值 | `16` |

两点注意：

1. 思路与已有的 `SGLANG_DS41_LMHEAD_ROW_CHUNK` 相同：每次调用都是普通 decode
   本来就会发出的形状。
2. 该 env 在**模块 import 时读一次**（`deterministic.py:154` 的
   `_MHC_MIX_ROW_CHUNK`），不是每次调用读。改值必须重启进程，不能热切换。

## 已自证什么

在 gfx942、`K=20480`、`MIX=24`、3 组随机 draw、`M ∈ {16, 32, 64, 128}` 下：

1. **默认关 = 今天**：不打补丁的树与打了补丁但 env 未设的树逐位相同（**12/12**
   形状 × 种子）；默认值不改变任何东西。
2. **开启后跨 M 稳定**：env=16 时，`M = 32/64/128` 的 rows `0..15` 与 16 行批次
   `torch.equal`（**12/12**，maxdiff 0）；两次独立进程启动（各自重新跑一遍
   Triton autotune）也逐位一致（12/12）。
3. **负向对照**：在未打补丁的树上同样的检查 **FAIL**（exit 1，三个种子的 maxdiff
   分别为 `3.662e-04` / `2.098e-05` / `2.289e-05`），说明验证器不是空转的。

`M <= 16` 完全不受影响：只有超过 chunk 大小的行才改变算术。

## 代价

同形状早先测的比值：M=32 `1.90x`、M=64 `1.61x`、M=128 `1.61x`，
即每次调用 **+0.033 / +0.049 / +0.091 ms**。相对倍数有误导性 —— 一个 decode step
是几十 ms，绝对增量大概率在噪声量级。端到端代价仍要由门禁测，这里不推断。
